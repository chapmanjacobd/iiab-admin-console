# syncweb integration

syncweb is an optional Rust daemon. It is deliberately installed as a
separate systemd service rather than added as a dependency of the Admin
Console's Python command server.

## Enable installation

Set these variables in `vars/local_vars.yml` on the IIAB host:

```yaml
syncweb_install: true
syncweb_enabled: true
syncweb_install_source: registry
syncweb_crate: syncweb
syncweb_version: 0.1.1-alpha.12
syncweb_peer_ticket: "syncweb://folder/..."
```

For a development checkout instead of the published crate:

```yaml
syncweb_install: true
syncweb_install_source: local
syncweb_source: /opt/syncweb
syncweb_cargo_path: /opt/syncweb/syncweb-cli
```

With `syncweb_install_source: registry`, the role installs the published
`syncweb` crate using
`cargo install --locked syncweb@0.1.1-alpha.12 --root /usr/local`. A version
must be pinned, because the crate has no stable release that contains the real
CLI yet (`0.1.0` is a placeholder). Update `syncweb_version` to move to a newer
release. `0.1.1-alpha.12` is the first release whose `folders join` accepts `-`
to read the ticket from standard input, which keeps the ticket out of the
client's process arguments. With `syncweb_install_source: local`, `syncweb_cargo_path` must exist
on the target host; the workspace root is virtual, so the development path is
its `syncweb-cli` member. Registry mode needs Cargo registry access during
installation; local mode is useful for development or an otherwise offline
target when the checkout is already present. Both modes install Cargo if
needed, create a dedicated
`syncweb` data directory, and supervise the daemon with `syncweb.service`. The
role checks the installed CLI version and reinstalls a registry binary when
`syncweb_version` changes. The default service account is a dedicated
`syncweb` user. Grant that user access to any folder it should synchronize, or
override `syncweb_user` and `syncweb_group`. When reusing an existing account,
also set `syncweb_manage_user: false` so the role does not modify that account.

Set `syncweb_enabled: false` to install the role but leave the service stopped
and disabled. The name follows the IIAB `<role>_enabled` convention, so moving
the role into the IIAB repository later needs no variable changes. Note that
**Run Ansible Roles** cannot manage syncweb while the role lives in this
repository: that command builds its playbook in the IIAB repository, where only
IIAB roles are resolvable. Install and configure syncweb with `./install`.

Run the normal installer after setting the variables:

```sh
./install
```

The default data directory is `/var/lib/syncweb/data`, and the media endpoint
is bound to `127.0.0.1:9193`. The service does not create or join folders
automatically because join tickets and write permissions are deployment
specific.

## Fetch selected content from another IIAB

When `syncweb_install` is enabled, Install Content shows a **From another
IIAB** source. If `syncweb_peer_ticket` is configured, it is prefilled and
used automatically; an administrator can replace it in the UI for a
one-off alternate source. The default ticket is intentionally public within
the deployment, while an override is visible to the administrator entering
it. Select the desired ZIMs and/or OER2Go modules in their usual catalog
lists, then choose **Fetch Selected Content**. The browser sends the ticket
and catalog IDs to CMDSRV; it never connects to syncweb directly.

`syncweb.service` must be running: the fetch helper refuses to start when it is
not, because the syncweb client would otherwise launch an unsupervised daemon
that holds the store lock and the media port, leaving the service unable to
start afterwards.

The source IIAB's shared folder uses the catalog paths as package names. Each
package may be a single file or a directory:

```text
zims/<file_ref>.zim
modules/<moddir>/<module files>
```

`file_ref` comes from the IIAB Kiwix catalog and `moddir` comes from its
OER2Go catalog. The package names are `zims/<file_ref>.zim` and
`modules/<moddir>`, which keeps the published collection identity aligned with
the shared-folder path. Create the dedicated shared folder from that directory
and publish it read-only:

```sh
sudo -u syncweb syncweb --data-dir /var/lib/syncweb/data \
  folders create --import --mode sendonly /var/lib/syncweb/content
```

Then publish each package separately, using the namespace that `folders create`
printed. For a ZIM package, use its containing directory as `--root` so the
file keeps its filename in the package manifest:

```sh
sudo -u syncweb syncweb --data-dir /var/lib/syncweb/data \
  package add --root /var/lib/syncweb/content/zims \
  --name zims/<file_ref>.zim --version 1.0.0 \
  /var/lib/syncweb/content/zims/<file_ref>.zim
sudo -u syncweb syncweb --data-dir /var/lib/syncweb/data \
  package publish --root /var/lib/syncweb/content/zims \
  --namespace <namespace> --sequence 1 \
  /var/lib/syncweb/content/zims/<file_ref>.zim
```

For an OER2Go module, use the same pattern:

```sh
sudo -u syncweb syncweb --data-dir /var/lib/syncweb/data \
  package add --root /var/lib/syncweb/content/modules/<moddir> \
  --name modules/<moddir> --version 1.0.0 \
  /var/lib/syncweb/content/modules/<moddir>
sudo -u syncweb syncweb --data-dir /var/lib/syncweb/data \
  package publish --root /var/lib/syncweb/content/modules/<moddir> \
  --namespace <namespace> --sequence 1 \
  /var/lib/syncweb/content/modules/<moddir>
```

Each `package add` creates or updates the workspace manifest for that package
root, and `package publish` writes that package's manifest into the folder's
document store. Bump a package version and re-run its two commands whenever
that ZIM or module changes; do not combine multiple content items into one
manifest. Give the read-only ticket to the destination operator.

The destination joins the folder with metadata only and performs an initial
metadata-only reconciliation of the `collections/` path, then discovers the
named package manifests and downloads exactly the manifest-listed paths into
`/var/lib/syncweb/staging`, and then uses the existing ZIM and OER2Go
finalization workflows. ZIMs are moved into place with
`zim_install_move.sh`, which also refreshes the kiwix library and menus. It
does not join a peer folder directly into
`/library`, so interrupted transfers cannot leave production indexes or menus
half-updated. The staging directory is removed after a successful transfer and
kept (with a message naming the path) after a failure, so partially downloaded
content can be inspected or re-fetched.

The package manifest is the contract: only the files it lists are installed,
so content added to a package root after publication is not transferred or
copied into `/library`. The package's current head is selected by its package
name; there is no broad collection selector or extra-file policy in the
destination UI.

Every file the manifest lists carries a BLAKE3 content id and a size. syncweb
verifies each blob against the hash associated with the selected folder entry
while fetching it, and the helper compares that live path-to-hash mapping with
the package manifest before and after each selected download. If the source
changes a path to different content, the fetch fails rather than installing a
same-sized replacement. The helper prints each selected package manifest's
BLAKE3 hash in the job output.

Tickets are credentials, so the helper passes the join ticket on the client's
standard input (`folders join -`), never in its arguments. The ticket is stored
in the root-owned command-server SQLite job database, which the role enforces as
mode `0600`, so an interrupted job can recreate its runtime spec after a
reboot. It is also stored in a root-readable runtime job file while the job is
running; that file is removed when the helper exits, while the job database
retains the restart metadata. The syncweb client itself runs as the `syncweb`
service account, never as root, so everything it writes keeps the ownership of
`syncweb.service`. The command service replaces the ticket in the command text
it logs and stores with a placeholder while keeping the catalog selections, so
the ticket does not appear in logs or job listings and a restart can still
resume the job; the restart metadata that must retain the ticket lives only in
the root-only job database. A syncweb whose `folders join` cannot read the
ticket from standard input (anything older than `0.1.1-alpha.12`) fails the
fetch; there is no fallback that would expose the ticket in the process
arguments. Treat tickets as credentials: use read-only shares, rotate them when
no longer needed, and do not paste them into issue reports or shell history.

The configured ticket is rendered into the CMDSRV configuration and returned
through the authenticated Admin Console configuration request. Because this
deployment treats the default ticket as public and Admin Console operators as
trusted, the configuration remains readable by the normal CMDSRV deployment
users. Read-only limits publication, not download access: anyone who obtains
the ticket can fetch the shared content.

## Create or join a folder

Run these commands as the configured service account (shown as `syncweb`
below) so they use the same identity and data directory as the service:

```sh
sudo -u syncweb syncweb --data-dir /var/lib/syncweb/data \
  folders create --import --no-share /library/www/html
printf '%s' '<ticket>' | sudo -u syncweb syncweb --data-dir /var/lib/syncweb/data \
  folders join - /library/www/html
```

The `join -` form reads the ticket from standard input, keeping it out of the
process arguments. A syncweb that does not support it (anything older than
`0.1.1-alpha.12`) fails the command; there is no argument-based fallback.

Normally the systemd service is already running, so only the `folders create`
or `folders join` command is needed. Replace `syncweb` with the configured
account when `syncweb_user` is overridden. Use a read-only share unless peers
must write into the folder. Do not put `.syncweb` data, identities, join
tickets, or private configuration in this Git repository.

## Updating a local checkout

The role is idempotent and does not rebuild an existing binary. After pulling
new syncweb source, set `syncweb_force_reinstall: true` for one Admin Console
run, then reset it to `false`.
